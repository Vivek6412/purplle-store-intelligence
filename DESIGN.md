# System Architecture and Design

The Store Intelligence Platform is a decoupled, highly scalable pipeline designed to process raw retail CCTV footage and convert it into real-time business analytics via an asynchronous API.

## Architecture Overview

The system operates across three primary layers:
1. **Edge Computer Vision Pipeline**: Raw video files are ingested by `detect.py`, which leverages YOLOv8 to detect human subjects. These detections are passed into `tracker.py`, where ResNet50 assigns a stable visual "fingerprint" to track people persistently across frames, and a deterministic hash simulates their age and gender to preserve real-time CPU performance. A geometric zone classifier mathematically tracks when a person steps inside bounding polygons representing aisles (e.g., "Skincare" or "Billing").
2. **Time-Machine Simulation**: `stream_all.py` acts as a historical time machine. It reads the raw telemetry generated by the edge pipeline and mathematically reconstructs the timeline, intentionally throttling HTTP POST requests to the backend so the data flows exactly as it would in real-time.
3. **Cloud Analytics API**: Built entirely on FastAPI and PostgreSQL (`asyncpg`), this layer receives the high-frequency event stream, sanitizes it, and inserts it into a relational database. Endpoints then aggregate this data to expose unique visitor counts, queue times, and POS conversion rates.

## AI-Assisted Decisions

1. **Pydantic Chaotic Schema Adapters**
   - **How the LLM shaped the design**: When dealing with disorganized and unpredictable JSON payloads from different physical store branches (e.g., `event_time` vs `timestamp`, `id_token` vs `visitor_id`), the AI suggested utilizing Pydantic's `field_validator(mode='before')` to coerce and normalize the keys before strict validation.
   - **Agreed or Overrode?**: **Agreed.** This elegantly shielded the database layer from corrupt data and made the API incredibly resilient to messy edge devices.

2. **Re-Identification Threshold Calibration**
   - **How the LLM shaped the design**: The LLM generated the initial ReID (Person Re-Identification) matching logic with a strict cosine similarity threshold of `0.85`. The LLM assumed that a high threshold would prevent accidental ID swaps.
   - **Agreed or Overrode?**: **Overrode.** When running the actual video clips, a threshold of `0.85` was mathematically too strict. It caused catastrophic "Identity Fragmentation," where a single customer was counted as 19 different visitors just by turning their head or stepping into a shadow. I explicitly overrode the AI's logic and lowered the threshold down to `0.70`, which completely fixed the fragmentation issue while preserving distinct visitor identities.

3. **Multi-Store Memory State Files**
   - **How the LLM shaped the design**: For tracking visitors, the LLM proposed maintaining a simple, global `self.identities` dictionary in RAM.
   - **Agreed or Overrode?**: **Overrode.** A global memory state caused cross-store hallucination—a person detected in Store 1 (Bangalore) was accidentally merged with a similar-looking customer in Store 2 (Mumbai). I overrode the design and architected isolated `.pt` state files (e.g., `tracking_state_ST1008.pt`) to force a hard boundary between physical branches.
